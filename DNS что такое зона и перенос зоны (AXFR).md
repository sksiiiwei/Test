# DNS: что такое зона и перенос зоны (AXFR)

Oct 13, 2026 · @ercie p

## Основы: домен, поддомен, имя

DNS это распределённая база данных, которая переводит имена в данные: чаще всего в IP-адреса. Имя читается справа налево, а части между точками называются **метками** (labels).

```
lk.gidromash-service.ru.
│  │                  │ └─ корень (пустая метка, пишется как точка в конце)
│  │                  └─── ru: домен верхнего уровня (TLD)
│  └────────────────────── gidromash-service: домен второго уровня
└───────────────────────── lk: поддомен третьего уровня
```

| Термин | Что это | Пример |
| --- | --- | --- |
| Корень (root) | Вершина дерева DNS, пустая метка | `.` |
| TLD (домен верхнего уровня) | Последняя метка имени. Бывают национальные (ccTLD: `.ru`, `.de`), общие (gTLD: `.com`, `.org`) и новые (`.pro`, `.shop`) | `ru` |
| Домен второго уровня | Имя, которое вы регистрируете у регистратора | `gidromash-service.ru` |
| Поддомен | Любое имя левее домена. Создаётся бесплатно и без регистратора: достаточно добавить запись в зону | `lk.gidromash-service.ru` |
| FQDN | Полное имя от корня, с точкой в конце | `lk.gidromash-service.ru.` |
| Апекс (корень домена) | Сам домен без меток слева, в зоне пишется `@` | `gidromash-service.ru` |
| Хост (hostname) | Имя, за которым стоит конкретная машина или сервис | `lk`, `www`, `mail` |

Правила имён:

- метка до 63 символов, всё имя до 253 символов;
- допустимы буквы a-z, цифры и дефис (не в начале и не в конце метки), регистр не важен;
- кириллические домены хранятся в виде **punycode**: `насосы-гидромаш.рф` превращается в `xn----7sbblfx3ackevgb0ipb.xn--p1ai` (так он и записан в вашем задании);
- уровней может быть много: `a.b.c.gidromash-service.ru` корректное имя.

Кто что регистрирует: домен второго уровня вы получаете у **регистратора** (в вашем задании Reg.ru). Он вносит данные в реестр зоны (для `.ru` это Координационный центр национального домена). Поддомены вы создаёте сами, без обращения к кому-либо.

## IP-адреса: у кого они и совпадают ли у имён

Нет, у домена и его поддоменов не обязан быть один IP. Каждое имя получает адрес из **своей** записи A (IPv4) или AAAA (IPv6), и записи независимы.

```
gidromash-service.ru.       A     95.213.184.77   ; сайт
www.gidromash-service.ru.   CNAME gidromash-service.ru.   ; тот же адрес, что у сайта
lk.gidromash-service.ru.    A     95.213.184.77   ; кабинет на том же сервере
mail.gidromash-service.ru.  A     203.0.113.25    ; почта на другом сервере
cdn.gidromash-service.ru.   CNAME d111.cloudfront.net.   ; сторонняя сеть доставки
```

Адреса в примере условные, кроме `95.213.184.77` из вашего задания.

**Типичные ситуации:**

| Ситуация | Что происходит |
| --- | --- |
| Много имён на одном IP | Нормально. Веб-сервер различает их по заголовку `Host` (и по SNI в TLS) и отдаёт разные сайты. Так устроен общий хостинг |
| Одно имя на нескольких IP | Несколько записей A. Клиенты получают их в разном порядке (round-robin), нагрузка делится |
| Имя на IP за балансировщиком | IP принадлежит балансировщику, а не конечному серверу |
| Имя на CDN | IP принадлежит сети доставки контента (Cloudflare, Akamai), настоящий сервер скрыт |
| Один и тот же IP в разных местах мира | Anycast: адрес анонсируется из многих точек, клиент попадает в ближайшую (так работают корневые DNS-серверы и CDN) |
| Имя без IP | Допустимо: у домена может быть только MX, TXT, или он вообще парковочный |

**Кому принадлежит IP-адрес.** Адреса раздаются по цепочке: IANA → региональный регистратор (RIR; для России и Европы это RIPE NCC) → провайдер или хостер (LIR) → клиент. Узнать владельца блока можно командой `whois 95.213.184.77` или в базе RIPE. Важно, что владелец **IP** и владелец **домена** это разные роли:

- домен можно направить на любой чужой IP, это просто запись в зоне;
- на IP хостера могут висеть сайты сотни разных клиентов;
- поэтому совпадение IP **не доказывает** общего владельца, а одно только количество доменов на адресе не доказывает общий хостинг.

Это как раз логика кейса 2 в вашем тестовом задании: решает не число доменов на IP, а то, кому эти домены принадлежат.

**IPv4 и IPv6.** IPv4-адрес это 32 бита (`95.213.184.77`), их не хватает, поэтому адреса дробят и прячут за NAT. IPv6 это 128 бит (`2001:db8::1`), записывается в AAAA. У одного имени может быть и то и другое одновременно.

## Кто есть кто в DNS

В разрешении имени участвуют разные роли. Их путают чаще всего, поэтому разберём по одной.

| Участник | Что делает | Пример |
| --- | --- | --- |
| Стаб-резолвер (stub resolver) | Маленькая программа в вашей ОС или браузере. Сама имена не ищет, а передаёт вопрос дальше и хранит локальный кеш | Служба DNS-клиента в Windows, `systemd-resolved` в Linux |
| Рекурсивный резолвер (recursive resolver) | Сервер, который по вашему запросу **сам** обходит всю цепочку серверов и возвращает готовый ответ. Хранит большой общий кеш | Провайдерский DNS, `8.8.8.8` (Google), `1.1.1.1` (Cloudflare) |
| Корневые серверы (root servers) | Знают только, кто отвечает за каждую зону верхнего уровня. Про `lk.gidromash-service.ru` они ничего не знают, но подскажут, где искать `.ru` | `a.root-servers.net` … `m.root-servers.net` |
| TLD-серверы | Знают, какие NS отвечают за каждый домен второго уровня в своей зоне | серверы зоны `.ru` |
| Авторитетные серверы (authoritative servers) | Хранят **настоящие** записи зоны и дают окончательный ответ. Не ищут ничего у других | `ns1.beget.com`, `ns2.beget.com` |
| Регистратор (registrar) | Компания, у которой вы покупаете домен и где указываете NS | Reg.ru |
| Реестр (registry) | Организация, которая ведёт зону TLD и базу всех доменов в ней | Координационный центр `.ru` |

**Корневые серверы подробнее.** Их 13 именованных адресов (буквы от a до m), которыми управляют около десятка организаций. Но физических машин сотни: каждый адрес размножен через anycast по всему миру, так что на запрос отвечает ближайшая копия. Рекурсивные резолверы заранее знают адреса корневых серверов из файла **root hints**, с него и начинается любой обход.

**Что значит «авторитетный».** Сервер авторитетен для зоны, если он хранит её и вправе давать на неё окончательный ответ. В ответе при этом стоит флаг `aa` (authoritative answer). Рекурсивный резолвер **не** авторитетен: он пересказывает то, что узнал у других, и поэтому его ответ может быть из кеша и устареть.

**Рекурсия и итерация.**

- Рекурсивный запрос: «найди мне ответ полностью» (клиент → резолвер).
- Итеративный запрос: «скажи, кого спросить дальше» (резолвер → корень, TLD, авторитетный). Каждый из них либо отвечает, либо отправляет к следующему.

**Что такое NS и glue** в этой цепочке: NS-запись это указатель «за эту зону отвечают такие серверы». Glue это адрес сервера имён, который родитель хранит сам, когда имя сервера лежит внутри делегируемого домена (иначе пришлось бы искать сервер, чтобы найти сервер).

## Как происходит разрешение имени: пример

Разрешение (resolution) это путь от имени до ответа. Возьмём случай, когда вы открываете `lk.gidromash-service.ru` и **ничего не закешировано** (самый длинный путь).

1. **Браузер и ОС.** Браузер смотрит в свой кеш, затем ОС проверяет файл `hosts` (`/etc/hosts` в Linux, `C:\Windows\System32\drivers\etc\hosts` в Windows) и свой кеш. Пусто, значит вопрос уходит стаб-резолвером к рекурсивному резолверу (адрес задан в настройках сети, например `1.1.1.1`).
2. **Рекурсивный резолвер** смотрит в свой кеш. Тоже пусто. Начинает обход с корня.
3. **Вопрос корневому серверу:** «где `lk.gidromash-service.ru`?» Ответ: «не знаю, но за `.ru` отвечают вот эти серверы» (это NS-записи зоны `.ru` и их адреса).
4. **Вопрос серверу `.ru`:** то же самое. Ответ: «за `gidromash-service.ru` отвечают `ns1.beget.com` и `ns2.beget.com`». Это и есть делегирование, которое вы задавали у регистратора.
5. **Вопрос авторитетному серверу `ns1.beget.com`:** «какая запись A у `lk.gidromash-service.ru`?» Ответ с флагом `aa`: `95.213.184.77`, TTL 3600.
6. **Возврат.** Резолвер кеширует ответ на 3600 секунд и отдаёт его стаб-резолверу, тот браузеру. Браузер открывает соединение по этому IP.

Этот же путь можно увидеть вживую:

```
$ dig +trace lk.gidromash-service.ru

.                      518400  IN  NS   a.root-servers.net.   ; корень
...
ru.                    172800  IN  NS   a.dns.ripn.net.       ; делегирование .ru
...
gidromash-service.ru.  86400   IN  NS   ns1.beget.com.        ; делегирование домена
gidromash-service.ru.  86400   IN  NS   ns2.beget.com.
lk.gidromash-service.ru. 3600  IN  A    95.213.184.77         ; итоговый ответ
```

Значения TTL и имена серверов условные, ради структуры. Реальный вывод у вас будет длиннее.

**Второй раз быстрее.** Если через минуту вы спросите `www.gidromash-service.ru`, резолвер уже знает, кто обслуживает `.ru` и `gidromash-service.ru` (эти NS в кеше), и сразу идёт к `ns1.beget.com`: корень и `.ru` пропускаются. Если спросить тот же `lk` ещё раз, ответ придёт прямо из кеша без единого внешнего запроса.

**Отрицательный ответ тоже кешируется.** Если имени нет (NXDOMAIN), этот факт запоминается на время из поля `minimum` в SOA, чтобы не спрашивать одно и то же снова.

**Что можно проверить на каждом шаге:**

```
dig lk.gidromash-service.ru                     # через ваш резолвер (может быть кеш)
dig @ns1.beget.com lk.gidromash-service.ru      # напрямую у авторитетного, без кеша
dig @1.1.1.1 lk.gidromash-service.ru            # через конкретный публичный резолвер
```

Если ответ от авторитетного сервера новый, а от резолвера старый, дело в TTL: старая запись ещё живёт в кеше.

## Где и что хранится

Никто в мире не хранит все записи сразу. Данные распределены по уровням, и каждый уровень знает только свою часть.

| Где | Что хранит | Как долго |
| --- | --- | --- |
| Файл `hosts` на вашем компьютере | Ручные соответствия «имя → IP». Проверяется раньше DNS и перекрывает его | Пока вы не измените файл |
| Кеш браузера и ОС | Недавние ответы | До конца TTL (браузеры часто ограничивают сами, на минуты) |
| Кеш рекурсивного резолвера | Ответы всех его клиентов, а также NS-цепочки (`.ru`, домены) | До конца TTL каждой записи |
| Файл root hints на резолвере | Имена и адреса 13 корневых серверов, точка входа для обхода | Редко меняется |
| Корневая зона (на корневых серверах) | Только делегирования: список TLD (около полутора тысяч) и их NS | Обновляется централизованно |
| Зона TLD (серверы `.ru`) | Для каждого домена второго уровня: его NS, glue, ключи DS | Пока домен зарегистрирован |
| Авторитетные серверы домена | **Все** записи вашей зоны: A, MX, TXT, CNAME и другие | Пока вы их не удалите |
| Реестр и регистратор | Данные регистрации: владелец, даты, статус (то, что видно в `whois`) | Срок регистрации (`paid-till`) |

**Масштаб.** Корневая зона маленькая: она содержит не сайты, а только указатели на TLD, поэтому её копию можно держать где угодно. Зона `.ru` огромная (миллионы доменов), но в ней у каждого домена всего несколько служебных записей. Реальное содержимое, то есть адреса ваших сайтов, лежит только у авторитетных серверов вашего домена. Благодаря этому система масштабируется: каждый хранит малую часть и знает, к кому отправить дальше.

**Что именно записано в зоне TLD для вашего домена** (то, что вы задаёте у регистратора):

```
gidromash-service.ru.  NS  ns1.beget.com.
gidromash-service.ru.  NS  ns2.beget.com.
```

Если здесь изменить NS, весь домен «переедет» на другие DNS-серверы, а записи из старой зоны перестанут использоваться. Именно поэтому доступ к аккаунту регистратора критичен для безопасности: тот, кто меняет NS, контролирует весь домен.

**Кеш и TTL на практике.** Вы поменяли A-запись, а сайт «ещё старый». Это не ошибка: у резолверов по всему миру копии записи живут до конца TTL. Поэтому перед переездом TTL заранее снижают (до 300 секунд), а после переезда возвращают.

## Что такое зона

Зона это участок дерева DNS, за который отвечает один и тот же набор серверов и который описан одним файлом. Зона и домен не синонимы: домен это логическая ветка имён, зона это та часть ветки, которую администрирует один хозяин.

Если у `gidromash-service.ru` нет делегированных поддоменов, весь домен лежит в одной зоне. Если `lab.gidromash-service.ru` отдан другим серверам, он становится отдельной зоной, хотя по имени остаётся частью домена.

Файл зоны состоит из трёх частей: запись SOA (паспорт зоны), записи NS (кто авторитетен) и все остальные записи (A, MX, TXT, CNAME и так далее).

```
$ORIGIN gidromash-service.ru.
$TTL 3600
@    IN SOA ns1.beget.com. hostmaster.beget.com. (
          2026101301 7200 3600 1209600 3600 )
@    IN NS  ns1.beget.com.
@    IN NS  ns2.beget.com.
@    IN A   95.213.184.77
lk   IN A   95.213.184.77
www  IN CNAME gidromash-service.ru.
@    IN MX  10 mx1.beget.com.
```

Здесь `$ORIGIN` задаёт имя, которое дописывается к коротким меткам, а `@` означает саму зону.

## Делегирование и границы зон

Граница между зонами проходит там, где родитель делегирует поддерево другим серверам. Делегирование это запись NS в родительской зоне, которая говорит: за это имя отвечают вот эти серверы.

```
.                          зона корня (13 групп корневых серверов)
└── ru.                    зона .ru (серверы координационного центра)
    └── gidromash-service.ru.   зона клиента (ns1/ns2.beget.com)
        └── lab.gidromash-service.ru.   отдельная зона, если делегирована
```

Когда вы указываете NS у регистратора, вы вносите запись делегирования в зону `.ru`. Именно её видит `dig +trace`.

Если сервер имён лежит внутри самого делегируемого домена (`ns1.example.ru` для `example.ru`), родитель обязан хранить его адрес: это glue-запись. Без неё получился бы замкнутый круг: чтобы найти NS, нужен адрес NS.

Для разведки периметра это важно: делегированный поддомен живёт на других серверах, и его записи нельзя увидеть через зону родителя. Отдельная зона может принадлежать подрядчику, у которого другие настройки защиты.

## Первичный и вторичный серверы

У зоны есть один источник правды и несколько копий. Это нужно для отказоустойчивости: если один сервер упал, остальные продолжают отвечать.

| Роль | Что делает |
| --- | --- |
| Первичный (primary, master) | Хранит редактируемый файл зоны. Админ вносит изменения здесь |
| Вторичный (secondary, slave) | Хранит копию, сам её не редактирует, а забирает у первичного |

Вторичный сервер получает копию именно через **перенос зоны**. С точки зрения клиента разницы нет: оба сервера авторитетны и отвечают одинаково. Поэтому в `dig NS` вы видите оба, не зная, какой из них первичный.

У большинства хостеров (Beget, Reg.ru, Cloudflare) всё это скрыто: вы правите записи в панели, а перенос между их серверами делают сами.

## Перенос зоны: AXFR и IXFR

Перенос зоны это копирование всех записей зоны с одного DNS-сервера на другой по протоколу TCP, порт 53. Полный перенос называется AXFR, перенос только изменений IXFR.

Как это идёт:

1. Админ меняет запись на первичном сервере и увеличивает `serial` в SOA (например, `2026101301` → `2026101302`).
2. Первичный шлёт вторичным сообщение NOTIFY: «зона изменилась».
3. Вторичный запрашивает у первичного SOA и сравнивает serial со своим. Если у первичного он больше, нужно обновляться.
4. Вторичный отправляет запрос AXFR (или IXFR, если поддерживается), и первичный отдаёт все записи зоны одним потоком.
5. Если NOTIFY потерялся, вторичный всё равно проверяет serial сам, раз в `refresh` секунд из SOA.

Именно поэтому ошибка «забыли увеличить serial» ломает синхронизацию: вторичный считает, что новых данных нет.

Важная деталь: AXFR отдаёт **всё без фильтрации**, включая внутренние и забытые имена. Поэтому первичный сервер должен разрешать перенос только IP-адресам своих вторичных серверов (ACL или подпись TSIG).

## Чем опасен открытый AXFR

Если сервер отдаёт перенос зоны кому угодно, любой человек получает полный список записей домена одним запросом. Это раскрывает карту инфраструктуры: все поддомены (включая dev, test, vpn, internal), IP-адреса, почтовые серверы, TXT-записи с верификациями и иногда внутренние имена.

Для злоумышленника это замена перебору поддоменов: быстро, тихо и полно. Для пентестера это проверка в самом начале разведки и находка уровня low или medium, а на серьёзную тянет, если в зоне видны внутренние адреса.

**Как проверить** (только на периметре клиента и в рамках договора):

```
dig NS example.ru +short
dig AXFR example.ru @ns1.example.ru
```

Проверять надо **каждый** NS из списка, потому что настройки у серверов могут отличаться.

| Ответ | Что значит |
| --- | --- |
| Список записей, в конце снова SOA | Перенос открыт, находка подтверждена |
| `Transfer failed` или `REFUSED` | Перенос закрыт, всё в порядке |
| Таймаут | TCP 53 закрыт или фильтруется |

**Как защищаться:**

- разрешить AXFR только по ACL для IP вторичных серверов;
- подписывать переносы ключом TSIG;
- закрыть TCP 53 для всех остальных на межсетевом экране;
- не хранить в публичной зоне внутренние имена: для них нужна отдельная внутренняя зона (split-horizon).

## Wildcard-записи: примеры и подводные камни

Wildcard (запись-«джокер») это запись, в которой самая левая метка равна `*`. Она отвечает за **все имена, которых нет в зоне**. Её используют как «запасной вариант», когда для имени нет своей записи.

**Пример зоны:**

```
$ORIGIN example.ru.
@      A   95.213.184.77     ; сам домен
lk     A   95.213.184.77     ; личный кабинет
mail   A   203.0.113.25      ; почта
*      A   178.210.92.7      ; всё остальное
```

**Что вернёт DNS на разные вопросы:**

| Запрос | Ответ | Почему |
| --- | --- | --- |
| `A lk.example.ru` | 95.213.184.77 | У имени есть своя запись, wildcard не нужен |
| `A mail.example.ru` | 203.0.113.25 | То же самое |
| `A qx7zn2vlk9m4.example.ru` | 178.210.92.7 | Имени нет, срабатывает `*` |
| `A backup-old.example.ru` | 178.210.92.7 | Имени тоже нет, срабатывает `*` (так в кейсе 3 вашего задания) |
| `A a.b.example.ru` | 178.210.92.7 | Wildcard покрывает и несколько уровней, пока на пути нет существующих имён |
| `A example.ru` | 95.213.184.77 | Апекс имеет свою запись. Даже без неё `*` апекс не покрывает |
| `A x.lk.example.ru` | NXDOMAIN | Имя `lk` существует, поэтому `*.example.ru` его вложенные имена уже не закрывает |
| `MX lk.example.ru` | пустой ответ (NOERROR) | Имя существует, но MX у него нет. Wildcard не подставляется, если имя есть, даже с другим типом записи |

**Правила, которые стоит запомнить:**

1. Звёздочка работает **только как вся самая левая метка**: `*.example.ru` это wildcard, а `a*.example.ru` или `x.*.example.ru` нет (там `*` это обычный символ).
2. Wildcard применяется, **только если имени нет вообще**. Как только у имени появилась любая запись, wildcard для него перестаёт действовать полностью, для всех типов.
3. Наличие любого имени **ниже** тоже «создаёт» промежуточное имя. Если есть запись для `www.dev.example.ru`, то `dev.example.ru` существует как пустой узел и wildcard на него не распространяется.
4. Wildcard не покрывает апекс.
5. Wildcard бывает любого типа: A, AAAA, CNAME, MX, TXT.

**Другие виды wildcard:**

```
*.example.ru.        CNAME  shops.myshopify.com.   ; все неописанные имена как алиас
*.example.ru.        MX     10 mx1.example.ru.     ; почта на любой поддомен
*.apps.example.ru.   A      203.0.113.50            ; только внутри ветки apps
*.dev.example.ru.    A      10.0.0.5                ; только для dev-окружений
```

Запись `*.apps.example.ru` закрывает `x.apps.example.ru`, но не `x.example.ru`: wildcard действует в пределах своей ветки.

**Зачем wildcard используют законно:**

- SaaS, где у каждого клиента свой адрес вида `клиент.сервис.ru`, и заводить запись на каждого не нужно;
- хостер парковывает все ещё не подключённые имена на одну страницу-заглушку;
- тестовые окружения: `pr-123.dev.example.ru` появляется автоматически;
- «ловушка» для опечаток в адресах.

**DNS-wildcard и wildcard-сертификат это разные вещи.** Сертификат `*.example.ru` (TLS) разрешает серверу доказывать, что он `a.example.ru`, `b.example.ru` и так далее, но не `a.b.example.ru` и не `example.ru`. Он никак не связан с тем, как зона отвечает на запросы.

**Как определить wildcard** (пентест, разведка):

```
dig +short A qx7zn2vlk9m4.example.ru     # случайное имя
dig +short A pp31hsdv8t0c.example.ru     # ещё одно
```

Если случайные несуществующие имена получают IP, это wildcard. Дальше сравните HTTP-ответ случайного имени и кандидата: код, размер, `<title>`. Совпали, значит кандидат ничем не отличается от случайной строки, и реального ресурса за ним нет. Проверку делайте и на вложенных уровнях (`x.apps.example.ru`), потому что wildcard может быть только в ветке.

**Чем wildcard опасен:**

- **Захват поддомена (subdomain takeover).** Если `*` ведёт на сервис, где можно «добавить свой домен» без подтверждения владения, чужой человек привяжет туда `evil.example.ru` и разместит свой контент от вашего имени.
- **Фишинг.** Любое правдоподобное имя вроде `login-secure.example.ru` резолвится, хотя компания его не создавала.
- **Ложные находки при инвентаризации.** Перебор поддоменов по словарю выдаёт тысячи «существующих» имён. Без фильтрации wildcard отчёт загрязняется мусором.
- **Лишняя поверхность атаки.** Веб-сервер отвечает по любому `Host`, и на нём могут оказаться непредназначенные для публики приложения.
- **Приём почты на любое имя**, если wildcard MX есть, а SPF и DMARC на этих именах не настроены.

**Что рекомендовать клиенту:** убрать wildcard, если он не нужен; если нужен, направить его на свою инфраструктуру, а не на парковку у хостера; убедиться, что хостер не даёт привязать чужое имя без проверки владения; не использовать маски `*.example.ru` в allowlist для CORS, CSP и OAuth.

## Шпаргалка

| Вопрос | Ответ |
| --- | --- |
| Что такое зона | Участок дерева DNS под управлением одного набора серверов, описанный одним файлом |
| Чем зона отличается от домена | Домен это ветка имён, зона это её часть без делегированных поддоменов |
| Что создаёт границу зоны | Запись NS в родительской зоне (делегирование) |
| Что такое glue | Адрес NS, который родитель хранит сам, если NS лежит внутри делегируемого домена |
| Что такое перенос зоны | Копирование всех записей с первичного сервера на вторичный по TCP 53 |
| AXFR и IXFR | Полный перенос и перенос только изменений |
| Что запускает обновление | Рост serial в SOA, сообщение NOTIFY или таймер refresh |
| Чем защитить перенос | ACL по IP вторичных серверов и подпись TSIG |
| Как проверить открытый AXFR | `dig AXFR домен @каждый_NS` |

Команды для практики:

```
dig NS example.ru +short
dig SOA example.ru +short
dig example.ru +trace
dig AXFR example.ru @ns1.example.ru
```
